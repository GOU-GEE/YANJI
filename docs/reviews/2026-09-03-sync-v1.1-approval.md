# 二、Workspace 与实体 ID

保留多 Workspace 能力。

普通业务实体继续：

```text
UUIDv7
```

但是“逻辑上天然唯一”的实体不能仅使用：

```text
daily_review:2026-09-03
```

这种跨 Workspace 会碰撞的 ID。

每日复盘正式改成 Workspace 作用域确定性 ID：

```text
daily_review/{workspace_id}/{YYYY-MM-DD}
```

例如：

```text
daily_review/01991f82.../2026-09-03
```

因此：

```text
id
```

仍然可以继续作为全局主键。

同时保留数据库约束：

```text
UNIQUE(workspace_id, review_date)
```

作为第二层保护。

以后其他确定性实体采用相同原则：

```text
{entity_type}/{workspace_id}/{logical_key}
```

# 三、origin_seq 正式改为 Workspace 内递增

不使用：

```text
设备全局 origin_seq
```

正式定义为：

```text
(workspace_id, origin_device_id)
```

拥有独立序列。

例如同一 iPhone：

```text
Workspace A

1
2
3
4
```

同时：

```text
Workspace B

1
2
3
```

数据库唯一约束：

```text
UNIQUE(
    workspace_id,
    origin_device_id,
    origin_seq
)
```

Frontier 同样始终属于 Workspace：

```text
Workspace
  ├─ Phone → 1032
  ├─ iPad  → 842
  └─ Mac   → 391
```

这样不会因为多个 Workspace 交错写入产生永久序号空洞。

# 六、Operation 增加因果上下文

仅有 HLC 不足以判断：

> 两次修改是真的并发，还是一方已经看过另一方。

因此 Operation V1 正式增加：

```text
causal_context
```

它表示：

> 创建当前 Operation 时，本设备已经观察到的各 Origin 版本。

逻辑形式：

```text
Phone → 1032
iPad  → 842
Mac   → 391
```

Operation 本身拥有自己的：

```text
dot = (
    origin_device_id,
    origin_seq
)
```

于是实际上形成：

```text
Dot
+
Causal Context
```

这不是引入完整通用 CRDT。

它主要用于：

- 判断长文本修改是否真正并发；
- Trust 历史判断；
- 调试；
- 未来协议扩展。

# 七、因果关系正式定义

对于 Operation A 和 B：

如果同 Origin：

```text
A.seq < B.seq
```

则：

```text
A happens-before B
```

对于不同 Origin：

如果：

```text
B.causal_context[A.origin] >= A.origin_seq
```

则：

```text
A happens-before B
```

如果：

```text
A 没见过 B
```

且：

```text
B 没见过 A
```

则：

# A 与 B 并发

HLC 仍然用于：

> 两个并发版本之间选择确定性显示 winner。

但 HLC：

# 不再用于判断“是否并发”。

```text
loser copy
```

改进为：



确定一个 winner。

但另外一个版本不得丢失。

## 用户解决冲突

用户最终选择或合并以后：

产生新的 Operation C。

C 的 causal_context 必须已经观察：

```text
A
+
B
```

因此：

```text
C causally supersedes A
C causally supersedes B
```

版本集合自动重新收敛为：

```text
{C}
```

这种方式比依赖本机：

```text

```

生成 Conflict Copy 更可靠。

# 十一、Oplog 与 Projection 状态分离

一个 Operation 可以已经：

```text
安全持久化
```

但尚未：

```text
物化到业务 Projection
```

建议本机维护：

```text
apply_state
```

至少区分：

```text
applied

pending_entity_create

pending_dependency

pending_authorization

pending_schema
```

另外：

```text
invalid_signature
malformed
```

这类数据不应作为正常复制历史进入主 Oplog。

应记录在：

```text
sync error / quarantine
```

本机诊断区域。

# 十二、Unknown Schema 必须保留

如果收到：

```text
schema_version > 当前支持版本
```

但 Operation：

- Envelope 能解析；
- 身份合法；
- Signature 合法；

则：

```text
保存 Operation
```

状态：

```text
pending_schema
```

不进行 Projection Apply。

未来 App 升级以后重新 Replay。

并且该设备仍允许将这条 Operation Gossip 给其他支持新版本的设备。

# 十三、Operation 签名格式正式冻结

禁止：

```text
Ed25519.sign(jsonEncode(operation))
```

普通 JSON 不属于稳定签名格式。

Operation wire format 正式采用：

# RFC 8949 Deterministic CBOR

签名对象：

```text
Operation Envelope
```

Signature：

# 不属于 Envelope 本身。

即：

```text
signature =
Ed25519.sign(
    deterministicCbor(operationEnvelope)
)
```

---

# 十四、签名 Envelope 与本机 metadata 完全分离

签名内容只能包括不可变协议字段，例如：

```text

workspace_id

op_id

origin_device_id

origin_seq

hlc_wall_ms

hlc_counter

causal_context

entity_type

entity_id

action

payload_schema_version

payload
```

绝对不能包含：

```text
received_from_device_id

received_at_ms

applied

apply_state

retry_count

local_error
```

这些都是：

# Local Delivery Metadata

# 十五、接收端保存原始 signed bytes

本机创建 Operation 时：

```text
Canonical CBOR
↓
生成 envelope_bytes
↓
签名
```

网络发送：

```text
envelope_bytes
+
signature
```

接收端：

```text

```

而应该直接：

```text
Ed25519.verify(
    envelope_bytes,
    signature
)
```

然后：

```text
原样保存 envelope_bytes
```

这样未知 Schema 也可以被安全保存和转发。

# 二十一、Revoke 增加 cutoff_seq

`device.revoke` Payload 必须记录：

```text
target_device_id

max_allowed_origin_seq
```

例如：

```text
target:
Old iPhone

max_allowed_origin_seq:
981
```

含义：

来自旧 iPhone：

```text
seq <= 981
```

属于可接受历史。

```text
seq > 981
```

永远无效。

这样被移除设备即使仍拥有私钥：

也不能继续创建：

```text
#982
#983
#984
```

然后通过第三台设备 Gossip 回 Workspace。

---

# 二十二、Revocation 到达后必须能撤销已经错误应用的后续 Operation

例如：

Mac 先收到：

```text
OldPhone #982
```

当时还不知道它已被 revoke。

于是临时 Apply。

之后收到：

```text
device.revoke
cutoff=981
```

Mac 必须：

```text
标记 #982 为 unauthorized/revoked
```

并重新计算：

```text
#982 所影响实体的 Projection
```

不能保持已经应用的结果。

因此 Projection 必须始终是：

> 当前有效 Operation 集合的派生状态。

# 二十八、SQLite synchronous 正式改为 FULL

