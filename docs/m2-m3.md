# M2/M3 三设备收敛验证

本阶段依据 [批准规范](reviews/2026-09-03-m2-m3-approval.md)，复用生产 OperationWriter、签名、OperationApplier、Resolver 和 Drift/SQLite。测试没有业务参考模型，也没有 UI 或真实网络。

2026-09-03 验证通过：全量 92 项测试；M2 固定 19 项、M3 日常 10 × 200，以及 seed 完整重放测试均通过。flutter analyze、格式检查和独立签名向量复核通过。[执行记录与基线](validation/m2-m3-2026-09-03.md)。

## 组成与边界

- `test/support/convergence/device_harness.dart`：三个独立文件 `device_a.sqlite`、`device_b.sqlite`、`device_c.sqlite`，各自的 Ed25519 身份、ClockState、Oplog、Projection、Frontier 和 policy 数据。使用生产数据库连接配置（WAL/FULL/FK）。
- `restart` 真正关闭连接，重新创建数据库、IdentityService、Identity、Writer 和 Applier；重开前后比较 digest、Frontier、时钟、context、pending 状态和完整确定性快照。文件中的确定性私钥只是公开测试夹具，绝不注册为应用安全存储实现。
- `simulated_transport.dart`：六条单向字节队列；支持乱序、重复、延迟、失败投递、分区和恢复。它只读路由元数据，不读取业务 type/action/payload。Frontier Diff 搭配缺口上方的稀疏已存储清单补齐历史；drop 仅删除一次投递尝试。
- 授权夹具由显式信任的 A 签发 Signed Operation，经独立的测试 policy workspace 传播；每台设备保存自己的原始签名字节，经验证后供 `OriginLookup` 查询并事务内调用 `refreshAuthorization`。它只测试已确定 membership 决策的传播和生产重算，不是 Genesis、QR 或生产授权链实现。
- `random_scenario.dart`：单一 seed 控制动作、设备、实体、时间偏移和投递顺序。Operation ID 从设备和持久化序号确定性生成；应用默认仍为 UUIDv7。重放测试比较完整 trace、签名字节和最终状态指纹。

## 断言

固定场景覆盖间接 Gossip、独立离线编辑、1/2/10/100 次重复、create/update 的全部六种排列、字段并发、因果覆盖、MV 冲突和解决、删除及依赖闭包、晚到依赖、Owner Timer 乱序传播、真实重启、100 条历史中缺少 41–60 的补齐、授权 pending、cutoff=100 撤回 101/102、撤销经中间设备传播、future schema 和坏签名。

随机 workload 只生成 Subject、Task、DailyReview、StudySession，保留热门实体以提高冲突密度；删除其他实体以制造依赖回退。撤销消息可能尚未到达被撤销设备，因此它仍可按自己的旧 membership 产生 Operation，随后由 cutoff 排除。普通业务动作均走生产 Writer；只有 future-schema 和特殊低 HLC 协议夹具使用明确标注的签名/日志入口。

最终先停止新写入，再恢复全部链路，用有上限的 Frontier Diff + Gossip 循环补齐合法历史。验证五层结果：

1. 业务 projectionDigest 相同。
2. 七类业务表逐行逐字段相同；失败输出表、实体和字段。
3. FieldClock、Tombstone、MV 活动版本、物化状态、membership 和有效 Operation 状态相同。
4. Frontier 和 policy 历史相同。
5. 独立 SQL/domain invariant 检查：FK、Session/Segment 状态、Owner、永久删除、有效字段来源、实际字段值与 FieldClock 一致、未知/撤销历史不参与派生状态、MV 版本集合恰为因果极大集合。

本机接收时间、来源、retry、quarantine 不参与跨设备比较。超 cutoff 的历史禁止正常 Gossip，所以各库可能保留不同数量的已撤销 Operation；比较合法集合，并在各库单独检查撤销状态及其无派生影响。

每个随机场景都对三台设备分别 rebuildWorkspace，要求重建前后所有确定性状态相同，再进行跨设备比较。当前 Apply 本身就使用全 Workspace 重算，因此这验证的是持久化/replay 幂等与跨设备结果；没有声称已有独立的增量投影算法。

## 运行和重现

```sh
# 日常：M2 固定场景 + 10 seeds × 200 actions + seed 重放验证
./tool/run_convergence.sh pr

# 指定 seed（若只需要 M3，可直接指定 randomized_test.dart）
YANJI_SEED=202609030001 YANJI_ACTIONS=200 \
  .tooling/flutter/bin/flutter test test/convergence/randomized_test.dart --reporter expanded

# 可配置扩展；这些是运行入口，不能据此认定已执行
./tool/run_convergence.sh extended  # 默认 100 × 1000
./tool/run_convergence.sh soak      # 默认 100 × 2000
YANJI_SEEDS=20 YANJI_ACTIONS=300 ./tool/run_convergence.sh pr
```

失败输出 seed、失败步骤和最近 200 条动作，完整 trace/快照保存至 `.dart_tool/convergence/failures/`；`YANJI_ARTIFACT_DIR` 可指定 CI 收集目录。所有已发现的随机失败 seed 必须加入 `test/fixtures/regression_seeds.txt`，默认测试自动纳入。Shrinker 尚未实现，不阻塞当前 Gate。

本次随机 seed 没有失败，corpus 保留为空并注明原因；固定场景发现的未知 schema/digest 问题已由对应 M2 用例永久覆盖。

## 验证记录与性能

运行结果见 `docs/validation/` 和 CHANGELOG。每个 seed 输出操作数、投递次数、apply 总耗时、rebuild/digest 耗时、SQLite/WAL 大小、事件计数和可重放指纹，原始指标保存在 `.dart_tool/convergence/metrics/`。性能数据只作为后续比较基线，不设发布阈值。本轮保留全 Workspace 重算，不进行投影性能优化。

有限的固定场景和随机样本提供可复验的收敛证据，不构成对无限操作空间的数学证明。M3 Gate 通过后，开发顺序是基础业务 UI → 单设备可用 → 平台构建/真机验证 → LAN Transport。
